# 定时维护

## 工作流程

```text
官方来源变化 → 差异报告/候选 → 草稿PR（或Issue） → 人工核验并修订数据 → CI → 合入main → Pages
```

默认每周一北京时间09:00（UTC 01:00）运行`Official source audit`，也可在Actions里手动运行。它会：

- 对已登记的开放权重仓库读取当前提交和固定提交的公开配置，提取明确字段并对比；不会下载权重或执行模型代码。
- 比较SGLang目录及已收录recipe正文、vLLM支持表和指定官方发布页的内容指纹，报告新recipe路径。
- 在允许的作者账号下查找时间窗口内的新模型候选。每账号有读取上限，这不是对整个Hub的完整爬取。
- 生成`updates/pending.json`和`updates/report.md`；完整运行文件也作为Actions artifact保存。
- 对相同发现不重复创建开放PR；未变更且无读取异常时不创建更新单。

读取401/403/404、网络失败或限流时明确报告；不把这些状态解释为未披露、未发布或不支持。首次观察只建立对照，不表示参数变化或事实核验。

## 手动检查

```bash
npm run build
npm run sources:check
```

单纯检查不会改写`data/watch-state.json`或正式参数。首次建立监测对照/明确接受当前对照时：

```bash
python scripts/check_sources.py --bootstrap
```

新建项目时的对照是网络观察快照，和各字段的核验日期不同。`observed-state.json`是临时结果，不提交。定时维护提案把观察对照放进待审分支，只有合入后才成为新的对照。

## 处理候选

配置的专家、层数等变化可以按固定配置核验；总参数和激活参数仍需查模型作者原文。报告不会根据型号、文件大小或专家比例生成这些数字。新HF仓库可能只是量化或草稿，需分类后再决定是否建参数档案。

框架页面内容变化并不自动意味着支持级别变化。先查正文是否有具体部署、模板、架构或仅占位，再更新`data/framework-index.json`及相应参数档案。

## GitHub权限与退回方式

定时工作流只在受信任的`main`上由计划任务/手动触发。PR检查工作流没有写权限。来源检查生成候选分支；通常创建草稿PR。仓库若不允许机器人创建PR，脚本会退回创建Issue，附候选分支，供维护者手动发起PR；不自动批准、不自动合并。

首次部署可手动运行更新工作流并关闭“生成待审更新单”，只检查并保存artifact。成功后再按默认维护方式运行。

GitHub计划任务只在默认分支上执行，可能延迟；公开仓库长期无活动时可能被GitHub暂停。定期查看Actions最近运行状态，必要时重新启用。检查失败会标成失败，不能被当成一次成功核验。

可修改`data/upstreams.json`中的允许域名、作者账号、指定文档和候选读取上限；增加来源前先核验发布方身份。
